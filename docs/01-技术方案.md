## 1. 项目目标与范围

### 1.1 业务目标

覆盖企业一次完整绩效考核闭环：**周期配置 → 指标方案 → 目标下达与确认 → 过程材料留痕 → 期末自评/主管评 → HR 复核 → 管理层终审 → 结果确认 → 申诉复核 → 改进计划跟踪 → 归档**。

在此主线上叠加一个**纯规则的多因素辅助决策引擎**，为 HR/管理层输出"等级建议 + 因子贡献明细 + 置信度 + 是否需人工确认"，且系统建议与人工结论分表留痕、可追溯、可答辩演示。

系统采用 **Agent → 规则引擎 → RAG 三层智能结构**（Agent 已从加分项升级为**核心模块**，结构与能力详见 §6）：Agent 负责自然语言理解与编排；规则引擎提供确定性计算，并作为 Agent 的工具被调用；RAG 是制度条款、指标说明、历史案例的依据库。**决策内核始终是确定性规则：LLM 不直接打分、不直接给最终等级、不直接写业务表**。Agent 的三项核心能力为**方案起草、评价解释、异常巡检**，所有生成内容均为"草案"，经人工确认后才通过既有业务接口落库。Agent 必须带降级开关与规则模板兜底，任何 AI 故障不影响绩效主线。

### 1.2 使用角色

| 角色编码 | 角色名称 | 核心职责（系统内） |
|---|---|---|
| `EMPLOYEE` | 员工/业务经办人 | 确认目标、上传过程材料、自评、查看结果、确认/申诉、执行改进任务 |
| `DEPT_MANAGER` | 部门负责人 | 下达/调整本部门目标、评分初审、发起本部门改进计划、验证改进完成 |
| `HR_SPECIALIST` | HR 专员 | 建周期、维护指标库与方案、复核评分、处理申诉、维护规则配置 |
| `EXECUTIVE` | 管理层 | 终审与校准、查看全公司看板、担任申诉复核责任人（可配置） |
| `ADMIN` | 系统管理员 | 组织/用户/角色、系统参数、知识库、日志审计；不参与业务审批 |

数据范围（Data Scope）：员工仅本人；部门负责人为本部门及下级部门（按 `sys_dept.ancestors` 子树）；HR 与管理层为全公司；管理员只管系统数据，默认无业务数据查看权（看板除外）。

### 1.3 演示版交付范围（2026-12 月底）

1. 主线业务闭环全流程可走通（一个年度/季度周期，含 5 类角色账号）。
2. 决策引擎可对演示数据输出建议、因子明细、置信度，并演示人工调整留痕。
3. 审批流按"审批节点配置表"驱动，可在管理界面调整节点责任人（不做拖拽式流程设计器）。
4. 看板 3 张图表：等级分布、部门均分排名、周期趋势（待办以数字卡片+待办列表呈现，不单列图表）。
5. Agent 作为**核心模块**现场可见可用：方案起草、评价解释、异常巡检三项能力打通；打分与等级仍由规则引擎产出并留痕。开关关闭或模型故障时 Agent 自动降级为规则引擎模板文案，系统其余功能 100% 可用。
6. 2027 年 4 月答辩前的后续工作：测试补强、UI 打磨、答辩脚本数据（不改变本架构）。

### 2.2 后端分层与分包

根包：`com.epms`

| 包 | 职责 | 关键内容 |
|---|---|---|
| `com.epms.common` | 通用基础 | 统一响应体 `R<T>`、分页 `PageQuery/PageResult<T>`、错误码枚举 `ErrorCode`、业务异常 `BizException`、基类 Entity |
| `com.epms.config` | 框架配置 | MyBatis-Plus 配置（分页插件、乐观锁、逻辑删除）、Redis 序列化、CORS、Knife4j、线程池、Web 配置 |
| `com.epms.security` | 自写鉴权 | `JwtUtil`（签发/校验）、`JwtAuthFilter`、`UserContext`（ThreadLocal）、`@RequireRole` 注解与拦截器、数据范围拼装工具 |
| `com.epms.infra` | 基础设施 | `RedisLock`（SET NX PX 封装）、`RateLimiter`、`CacheKeys` 常量、`RedisRemindQueue`（ZSET 催办）、本地文件存储 `FileStorage` |
| `com.epms.modules.system` | 系统域 | 用户/部门/角色/参数/消息/操作日志 |
| `com.epms.modules.perf` | 绩效主线 | 周期、指标库、方案、目标、考评单、考评明细、材料版本、评分单、申诉、改进计划、结果结论 |
| `com.epms.modules.approval` | 审批域 | 节点配置、审批任务生成/签收/流转，与状态机解耦：节点配置只决定"生成什么任务、责任人是谁" |
| `com.epms.modules.engine` | 决策引擎（确定性内核） | `FactorCalculator`（6 个因子各一个实现类）、`HardConstraintChecker`、`GradeBander`、`DecisionTree`、`SnapshotService`、规则版本管理；另暴露无副作用纯计算入口 `evaluateDryRun` 供 Agent 工具调用（不写快照、不写业务表） |
| `com.epms.modules.ai` | **Agent 核心模块** | 三能力编排（方案起草 / 评价解释 / 异常巡检）、6 个只读 `@Tool`、Agent 调用日志 `agent_call_log`、降级 Fallback（规则引擎模板文案）、RAG 双路（智谱向量余弦 / BM25）、知识库管理 |
| `com.epms.job` | 定时任务 | 催办扫描（每分钟）、登录失败计数无需定时（Redis TTL）、改进计划逾期标记（每日 00:10）、周期到期提醒（每日 08:00） |

分层纪律：

- Controller 不写业务判断，只做：绑定/校验入参 → 调一个 Service 方法 → 包 `R.ok()`。
- 跨模块调用只能走对方 Service 接口，禁止 Mapper 越模块直连。
- 状态变更只允许经"状态机引擎"一个入口（`RecordTransitionService.fire(action, dto)`），任何 Service 不得直接 `update status`。
- 决策引擎只读业务表、只写 `perf_recommendation_snapshot`，**严禁**回写绩效分数/等级；写人工结论是独立接口。Agent 工具侧只能调用引擎的 `evaluateDryRun` 纯计算入口拿结果，正式快照仍仅由状态机规定的时机写入。
- **Agent 安全边界（强制）**：Agent 不允许持有任何业务表的写 Mapper；工具全部"只读 / 纯计算"；生成类能力只返回草案，落库一律走既有业务接口并经人工点确认；LLM 输出只用于"表达与编排"，分数与等级以规则引擎计算值为准，禁止用模型文本覆盖。

## 4. 鉴权与安全方案（自写，不使用 Spring Security）

### 4.1 登录与令牌

1. `POST /api/v1/auth/login` 校验账号密码（BCrypt，`sys_user.password_hash`）。
2. 签发双 Token：
   - `accessToken`：JWT，claims 含 `uid、username、jti`，有效期 2 小时；
   - `refreshToken`：随机 UUID（不存业务信息），有效期 7 天。
3. Redis 会话键（见 §5.1）。前端把双 Token 存内存（Pinia）+ `localStorage` 仅存 refreshToken；Axios 在 40101 时自动刷新一次并重放原请求。
4. 请求头：`Authorization: Bearer <accessToken>`。

### 4.2 过滤器与权限

- `JwtAuthFilter`：解析并校验签名/有效期 → 校验 Redis 会话存在且 jti 匹配 → 构造 `LoginUser` 放入 `UserContext` → 请求结束清理 ThreadLocal。
- `@RequireRole({RoleEnum.HR_SPECIALIST})` 注解 + 拦截器做角色控制；细粒度数据范围（本人/本部门子树/全公司）在 Service 层用 `DataScopeHelper` 拼 SQL 条件，不靠前端。
- 越权访问他人数据返回 `40301`；未登录 `40100`；Token 过期 `40101`；会话被顶号 `40102`。
- 密码策略：8 位以上含字母数字；连续 5 次登录失败锁账号 15 分钟（Redis 实现，§5.5）。
- 所有写操作记录 `sys_operation_log`（AOP 注解 `@OpLog(module, action)`，含操作前后 JSON 快照、IP、UA、traceId）。

## 5. Redis 的五个具体用途

Key 统一前缀 `epms:`，全部集中声明在 `CacheKeys`，禁止散落字符串。

### 5.1 会话共享（Session）

| 项 | 内容 |
|---|---|
| Key | `epms:auth:session:{userId}:{jti}` |
| Value | Hash：`username、realName、roleCodes、deptId、loginIp、loginAt、device` |
| TTL | 与 accessToken 对齐：2 小时，每次请求滑动续期（剩余不足 30 分钟时续到 2 小时） |
| 用途 | ① 过滤器校验会话存在性；② 退出登录/管理员踢人直接删 Key；③ refreshToken 另存 `epms:auth:refresh:{token}` → userId+jti，7 天；④ 同账号新登录可选"踢掉旧会话"（`sys_config` 中 `login.single-device` 开关） |
| 单机也要用的原因 | 实现主动失效与踢人；JWT 本身无法撤销 |

### 5.2 并发审核分布式锁（Lock）

| 项 | 内容 |
|---|---|
| Key | `epms:lock:appr:record:{recordId}`（申诉单、目标确认用各自 biz 前缀） |
| 取锁 | `SET key value NX PX 30000`，value=当前用户 ID+UUID，释放用 Lua 脚本比对 value 后删除，防误删 |
| 持锁时长 | 30 秒，覆盖一次"状态机校验→生成/完成审批任务→写库→写日志"事务；不续租（操作足够短） |
| 冲突处理 | 取锁失败直接返回 `40901 该单据正在被他人处理，请稍后重试`，前端按钮 loading 后可重试；不做排队等待 |
| 用途 | 防止两位审批人同时点"通过/退回"导致审批任务重复生成、状态覆盖 |

### 5.3 配置缓存（Cache）

| 项 | 内容 |
|---|---|
| Key | `epms:cache:config:sys`（系统参数 Hash）、`epms:cache:config:rules:{schemeId}`（某方案的因子权重/硬约束/分档规则 JSON） |
| TTL | 系统参数 10 分钟；规则缓存 30 分钟 |
| 更新 | 参数或规则保存时**主动删除对应 Key**（Cache-Aside），下一次读取回源并回填 |
| 用途 | 决策引擎每次计算都要读规则；登录拦截读限流阈值等；避免每次打 MySQL |
| 注意 | 规则快照的历史版本仍以 MySQL 的版本号字段为准，缓存不承担留痕职责 |

### 5.4 催办队列（Remind Queue）

| 项 | 内容 |
|---|---|
| Key | ZSET `epms:remind:approval`，member=`appr_task.id`，score=该任务"应催办时间戳" |
| 生产时机 | 审批任务生成时按节点期限写入（如生成后 24 小时未处理则催办）；任务完成时 `ZREM` |
| 消费方式 | `@Scheduled` 每分钟 `ZRANGEBYSCORE now-60s ~ now` 取到期 member，向 `sys_message` 插站内信（接收人=任务责任人），并把该 member 的 score 推进到下一次催办时间（默认再隔 24 小时，最多催 3 次，3 次后升级提醒其直属上级，次数存 task 字段） |
| 前端感知 | 轮询 `GET /api/v1/system/messages/unread-count`（60 秒一次），不做 WebSocket |

### 5.5 登录限流（Rate Limit）

| 项 | 内容 |
|---|---|
| Key | 失败计数 `epms:rl:login:fail:{username}`（String，INCR，首次 EX 900 秒，15 分钟窗口）；IP 维度 `epms:rl:login:ip:{ip}`（滑动窗口用 ZSET，member=时间戳+随机串，score=毫秒时间，窗口 1 分钟上限 20 次） |
| 阈值 | 同账号 5 次失败 → 锁 15 分钟（再设 `epms:rl:login:lock:{username}`，TTL 900）；同 IP 1 分钟 20 次 → 42900 |
| 成功登录 | 删除 fail/lock Key |
| 通用限流 | 对 `/api/v1/agent/**`（含 chat 与三能力接口）加每用户每分钟 10 次的 ZSET 限流，保护模型额度 |

## 6. 决策引擎、Agent 与 RAG 的定位

### 6.0 三层智能结构（核心设计）

```
┌─────────────────────────────────────────────────────────────┐
│ 第一层：Agent（理解与编排）  LangChain4j + glm-4-flash         │
│  自然语言交互、任务拆解、选择工具、把结构化结果组织成人话         │
│  输出全部是「草案/解释/报告」，不直接打分、不直接写业务表         │
└───────────────┬──────────────────────────────┬──────────────┘
                │ 调用（只读/纯计算工具）        │ 检索（依据）
┌───────────────▼──────────────┐  ┌────────────▼──────────────┐
│ 第二层：规则引擎（确定性内核） │  │ 第三层：RAG 依据库          │
│ 六因子+硬约束+权重+阈值+决策树│  │ 制度条款 / 指标口径说明 /    │
│ 输出分数、等级、置信度、依据   │  │ 历史相似案例               │
│ 结果可复算、可测试、可留痕     │  │ 智谱向量优先，BM25 兜底     │
└──────────────────────────────┘  └───────────────────────────┘
```

层级约束（开发与评审都按此检查）：

1. **分数、等级、置信度只能由第二层规则引擎产出**；Agent 可以解释、转述、对比，但不得自行生成或修改数值。
2. 第二层以两种方式被使用：① 状态机在规定时机正式调用 → 写快照；② Agent 通过 `evaluateDryRun` 工具临时调用 → 只返回不落库。
3. 第三层只提供"依据文本 + 出处"，不提供数值结论；Agent 回答中引用条款必须带文档名与章节路径。
4. Agent 对业务数据的访问只能通过 6 个只读/纯计算工具（§6.2），工具内部按角色做数据范围过滤。
5. 任一层故障的降级方向：LLM 挂 → Agent 用规则引擎结果套模板；embedding 挂 → RAG 走 BM25；规则引擎不允许挂（纯本地代码，其异常按 500 处理且阻断终审，不允许降级成模型打分）。

### 6.1 纯规则决策引擎（确定性内核，详见 04 文档）

- 位置：`modules.engine`，纯 Java 实现，零外部依赖；规则全部来自 MySQL 配置表（因子权重、硬约束、等级分档），规则带版本号。
- 触发时机（显式，不自动偷偷跑）：
  1. 员工提交自评后，生成一次"自评后建议"供主管参考；
  2. 部门评审通过后，生成"复核建议"供 HR/管理层参考（正式快照）；
  3. HR 也可在复核页手动点"重新计算"（规则未变则返回最新快照）。
- 每次输出**不可变**写入 `perf_recommendation_snapshot`；人工最终结论写 `perf_manual_conclusion`，两表通过 `snapshot_id` 关联但互不覆盖。
- 引擎绝不发起状态流转、绝不写绩效结果；它只是"被调用的计算器 + 留痕"。

### 6.2 Agent（核心模块）：能力、工具与强制边界

- 形态：全局右侧抽屉"绩效助手"，多轮对话，使用 LangChain4j 的 OpenAI 兼容客户端接入**智谱 BigModel**：
  - `base-url = https://open.bigmodel.cn/api/paas/v4`；
  - 对话模型固定用免费档 **`glm-4-flash`**，temperature 取 0.2（重事实、少发挥），调用总超时 8 秒；
  - API Key 只从环境变量 **`ZHIPU_API_KEY`** 读取（开发机可放 `backend/.env`，该文件必须写入 `.gitignore`）；代码、`application.yml`、注释、`seed.sql`、文档示例中只允许出现变量名与读取方式，**绝不出现密钥明文**。
- 六个工具（LangChain4j `@Tool`；全部**只读或纯计算**，Agent 自行决定调用，工具结果在回答中必须附出处）：

| # | 工具名 | 输入 | 输出 | 用途 |
|---|---|---|---|---|
| 1 | `queryIndicatorLibrary` | 关键字/分类/因子码 | 匹配的指标列表（编码/名称/单位/口径/默认因子） | 方案起草 |
| 2 | `querySchemeHistory` | 周期号/部门/岗位 | 历史方案及其指标项、权重、生效范围 | 方案起草参照 |
| 3 | `evaluateByRuleEngine` | recordId 或完整草案数据 | 规则引擎 `evaluateDryRun` 结果（因子分/约束命中/总分/建议等级/置信度/依据），**不写任何表** | 评价解释、草案权重试算 |
| 4 | `queryEmployeePerformance` | 员工（姓名/工号）+ 周期 | 绩效记录、因子分、等级、材料齐备情况 | 评价解释、问答 |
| 5 | `queryPolicyClause` | 自然语言问题 | 制度条款 chunk + 文档名/章节路径（§6.3 双路检索） | 解释附出处、方案合规核对 |
| 6 | `querySimilarCase` | 等级/关键字 | 历史已办结考评单（`status=CLOSED`）脱敏结论 | 对标参照 |
| 巡检 | `scanCycleAnomalies`（仅巡检接口编排调用，不挂到自由对话） | cycleId、异常类型集合 | 异常清单（见能力 C3），纯聚合查询 | 异常巡检 |

  工具内强制数据范围：员工角色只能命中本人数据；部门负责人限本部门子树；HR/管理层全公司。

- **三项核心能力**（均有独立页面入口，对话抽屉也能触发；接口契约见 03 文档 §4.14）：

| 能力 | 输入 | 处理与工具链 | 输出（均为草案/只读结果） | 落库方式 |
|---|---|---|---|---|
| **C1 方案起草** | 周期、作用域 + 自然语言需求（如"销售线，重业绩增长，兼顾新客户"） | `queryPolicyClause` 查制度口径 → `queryIndicatorLibrary` 选指标 → `querySchemeHistory` 参照权重 → `evaluateByRuleEngine` 对权重做合规试算（合计 100、硬约束齐全） | 方案草案：指标项清单（含建议权重与理由）、六因子权重建议、沿用的硬约束/分档版本、引用的制度条款与历史方案出处；字段结构与"创建方案"接口入参一致 | 用户在方案编辑页核对修改后，调既有 `POST /perf/schemes` + `POST /perf/schemes/{id}/publish` 落库；**生成接口本身不写库** |
| **C2 评价解释** | recordId（可指定 snapshotId） | `queryEmployeePerformance` 取数 → `evaluateByRuleEngine`（无最新快照时 dry-run）→ `queryPolicyClause` 附条款 | 自然语言解释：总分与等级、六因子得分及权重贡献、触发/逼近的硬约束阈值、异常点（评分差、缺失项），每条结论后挂制度条款出处；结构化字段同快照，保证"人话"和数值一一对应 | 不产生新数据；正式快照仍由状态机时机写入 |
| **C3 异常巡检** | cycleId（可勾选异常类型） | `scanCycleAnomalies` 只读扫描四类异常（见下）→ Agent 汇总成报告并给催办理由 | 巡检报告：异常项数组（类型/对象/严重度/证据数据/建议动作/可跳转 bizId）+ 汇总计数；四类异常：① 目标值异常偏离（与同岗位中位数偏离 >30% 或超历史 ±30%）；② 必交材料缺失（已提交但 `target_required=1` 指标无有效材料）；③ 自评与主管评分差 > `HC_SCORE_GAP` 阈值；④ 申诉超时（SUBMITTED 超 3 个工作日未受理） | 用户勾选异常项后点"生成催办"，调既有消息/催办接口写 `sys_message`；**巡检接口本身不写库** |

- 强制安全边界（Code Review 检查项）：
  1. Agent 代码路径中**禁止出现**任何业务表 insert/update/delete；`modules.ai` 只允许注入只读 Mapper 与 engine 的 dry-run 接口；
  2. 生成类接口（方案草案、巡检报告、解释）只返回数据，不改变任何业务状态；**凡要落库必须经对应人工确认接口**（方案发布、消息催办、结论确认）；
  3. LLM 返回的数字一律不采信：前端展示的分数/等级取结构化工具结果，模型文本仅作叙述；
  4. 每次能力调用写一条 `agent_call_log`（见 02 文档 §9.5），含工具链、采纳与否；
  5. 接口总超时 8 秒；超时、额度用尽、断网三种故障统一降级为规则引擎模板文案（见 §6.4），页面只提示"解释服务暂不可用"。
- 回答要求：先给结论，再列"依据"列表（工具名 + 数据对象/制度文档名称章节），无工具证据时明确说"未查到依据"。
- 会话与工具调用过程落库 `ai_chat_session / ai_chat_message`（含引用 JSON、是否走了降级），便于答辩展示。

### 6.3 RAG：双路检索，不引向量库

**首选路（语义向量）：**

```
制度文档(docx/pdf/txt)
  → 解析纯文本(PDFBox/POI)
  → 切块(约500字, 相邻重叠80字, 按段落优先切)
  → 调智谱 Embedding 接口(OpenAI 兼容 /embeddings；模型名以开通的免费档为准, 开工实测)
  → 向量以 JSON 数组字符串存 MySQL: ai_kb_chunk.embedding (TEXT 列)
  → 检索: SQL 先按启用状态/分类过滤取候选 chunk(演示级 < 2 万条),
          在 JVM 内做余弦相似度 top-k(k=4, 阈值 0.75)
```

**降级路（BM25/关键词，无需任何模型额度）：**

- 每个 chunk 落库时同步写 `tags`（制度条款标签，来自文档目录/人工标签，逗号分隔）与 `keywords`（标题分词 + 人工关键词）；
- 检索时对用户问题做中文分词（轻量词典或二元 bigram，不引重型分词依赖），按"标签命中权重 + 标题/正文 BM25 打分"取 top-k；
- BM25 参数：`k1=1.5、b=0.75`，标签命中按固定加分（实现常量，可配），按分排序。

**双路切换规则：**

1. 正常：智谱 embedding 可用且候选 chunk 中带向量的比例 ≥ 80% → 走向量路；
2. embedding **无免费额度 / 调用失败 / 超时（5 秒）/ 未配置 `ZHIPU_API_KEY`** → 本次检索自动走 BM25 路，回答中标注"当前为关键词检索结果"；
3. 单文档 embedding 失败只把该文档 chunk 置 `EMBED_FAILED`，不影响其他文档走向量路；管理页提供"重新生成向量"按钮；
4. 两路都属检索增强（RAG），**演示不能因额度问题中断**；当前使用的检索路记录在 `ai_chat_message.retrieval_mode`（`VECTOR`/`BM25`）。
- 不引入 pgvector/Milvus/FAISS/native 向量索引。
- 文档重新上传生成新版本 → 旧 chunk 逻辑删除，重新切块、打标签并嵌入（与材料版本同一套"留痕"思想）。

### 6.4 降级策略（必须实现，答辩演示点）

| 层级 | 触发条件 | 行为 |
|---|---|---|
| 全局开关 | `sys_config`：`ai.agent.enabled=false` | 三能力入口（方案页"AI 起草"按钮、考评单"AI 解释"面板、巡检页）置灰并提示未启用；后端 `/agent/**` 返回 `50301`；方案、考评、审批等主线零影响 |
| Agent 三场景降级 | ① 调用 `glm-4-flash` **超时（8 秒）**；② **额度用尽**（供应商返回 429/额度类错误）；③ **断网/连接失败** | 后端不重试、不抛 500：放弃模型生成，改用**规则引擎模板文案**兜底——直接取决策引擎快照中的等级建议、因子得分/权重贡献、依据列表，按固定中文模板拼装回答（数据真实、出处齐全）；接口仍 HTTP 200、响应体带 `degraded=true`；前端只在回答区顶部提示 **“解释服务暂不可用”**，绩效填报、审批、看板等主流程不受任何影响；消息落库标记 `degraded=1` |
| RAG 双路降级 | 智谱 embedding **无免费额度/调用失败/超时 5 秒/未配 `ZHIPU_API_KEY`**，或候选 chunk 向量覆盖率 < 80% | 当次制度问答自动切 **BM25/关键词路**（条款标签 + 标题/关键词匹配 + BM25 打分，见 §6.3），回答中标注“当前为关键词检索结果”；上传文档时嵌入失败仅把 chunk 标 `EMBED_FAILED`，不影响文件上传与 BM25 检索；检索路 `retrieval_mode=BM25` 落库，**演示不因额度中断** |
| 工具降级 | 任一 `@Tool` 执行异常 | 该工具返回"工具暂不可用"文本给模型，对话继续；单工具超时 5 秒 |
| 额度保护 | 每用户 10 次/分钟（Redis） | 超限返回 `42900`，提示稍后再试 |
| 启动安全 | 未配置 `ZHIPU_API_KEY` | 应用正常启动；`GET /agent/status` 返回 `enabled=true, healthy=false, reason=NO_API_KEY`；助手可打开，回答走规则引擎模板文案 + BM25 检索 |

## 8. 横切约定

| 主题 | 约定 |
|---|---|
| 统一响应 | 见 03 文档 §4；禁止 Controller 直接返回裸实体 |
| 逻辑删除 | 所有业务表带 `deleted TINYINT DEFAULT 0`，MyBatis-Plus `@TableLogic`；唯一约束按"未删除数据唯一"由应用层保证 |
| 审计字段 | 所有表含 `created_at/updated_at/create_by/update_by`；需要并发控制的表带 `version INT DEFAULT 0`（`@Version`） |
| 金额/分数 | 分数、权重一律 `DECIMAL(5,2)`，不用浮点；比率统一存"百分数值"（92.50 表示 92.5%） |
| 时间 | 一律数据库/服务端本地时间（`Asia/Shanghai`），不存前端传的时间；期限判定用服务端时间 |
| 事务 | 状态机 `fire` 整体一个事务：状态更新 + 审批任务 + 操作日志同提交/回滚；快照写入在事务内 |
| 异常 | 业务错误抛 `BizException(ErrorCode, msg)`，全局 `@RestControllerAdvice` 转统一响应体；不允许 `catch Exception` 后吞掉 |
| 接口文档 | 每个接口必须有 Knife4j 注解（summary、参数说明），与 03 文档的路径/错误码保持一致 |
| 前端权限 | 菜单与按钮按角色隐藏只是体验层，后端必须独立鉴权 |
| SQL 规范 | 表名蛇形小写、带模块前缀；索引名 `idx_`、唯一键 `uk_`；禁止存储过程/触发器/外键约束（逻辑外键，靠应用保证，方便演示库重放） |

## 9. 明确不做的清单（Non-Goals）

1. **不引** Spring Security 全家桶（只用自写 JWT 过滤器+拦截器）。
2. **不引** Flowable / Activiti / Camunda；不做 BPMN、不做会签以外的复杂网关（并行/包容/事件网关一律不做）。
3. **不引** 微服务、注册中心、配置中心、网关、Feign、Dubbo。
4. **不引** 消息队列（RabbitMQ/Kafka/RocketMQ）；催办用 Redis ZSET + 定时任务。
5. **不引** 向量数据库；不做 ANN 索引，RAG 只做 MySQL + JVM 内存余弦。
6. **不做**复杂运筹优化/线性规划/AI 大模型打分；决策引擎就是规则、权重、阈值、两三层决策树。
7. **不做**拖拽式流程设计器；节点配置通过 Element Plus 表单维护（节点顺序、责任人角色/指定人、会签方式、可否退回）。
8. **不做**移动端 App/小程序；不做企业微信/钉钉对接（组织数据在 `seed.sql` 内置）。
9. **不做**多租户、SSO/OAuth2 第三方登录、短信/邮件真实通道（消息只落站内信；邮件接口不写）。
10. **不做** WebSocket/SSE 实时推送；未读消息与待办用轮询。
11. **不做**在线 Office 编辑/文档预览；材料仅上传、下载、版本列表。
12. **不做**薪酬核算对接、考勤机对接、培训系统对接；考勤/培训数据由 HR 在页面录入或种子数据导入。
13. **不做**国际化多语言、不做深色主题、不做暗色模式以外的换肤。
14. **不做** Docker/K8s 部署脚本（演示用本机直跑；答辩如被问，口头说明水平扩展点=会话已在 Redis、锁已外置即可）。
15. Agent 不开放给员工查询他人绩效（工具内部按 `UserContext` 角色强制过滤；员工调 `queryEmployeePerformance` 只能查本人）。
16. 不写测试以外的脚本、不引入 Jenkins 流水线；测试以 JUnit5 核心引擎用例为主（对应 04 文档验证案例）。
