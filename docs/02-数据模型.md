# 02 数据模型（施工规格文档）

- 数据库：MySQL 8.0，库名 `epms`，`DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci`，表引擎统一 InnoDB。
- 全部 DDL 只允许落在 `db/schema.sql`；初始化数据落在 `db/seed.sql`。
- 命名：小写下划线，`sys_` 系统域、`perf_` 绩效域、`appr_` 审批域、`ai_` 智能域；索引 `idx_xxx`、唯一键 `uk_xxx`。
- 约定（适用于本文件所有表）：① 不建物理外键，只建逻辑外键（列注释标明引用），引用完整性由 Service 保证；② 枚举值存 `VARCHAR + 注释列出全部取值`，不用 MySQL ENUM；③ 分数字段统一 `DECIMAL(5,2)`（0.00–100.00），权重同理（0.00–100.00，同层合计 100）；比率一律存"百分数值"（如 80.00 = 80%）；④ 时间用 `DATETIME`，时区按 `Asia/Shanghai`；⑤ JSON 结构统一使用 `JSON` 列。

## 0. 通用约定

### 0.1 公共审计列（除特别说明外，每张业务表末尾都带）

| 字段名 | 类型 | 默认/约束 | 说明 |
|---|---|---|---|
| `id` | BIGINT UNSIGNED | PK AUTO_INCREMENT | 主键 |
| `create_by` | BIGINT UNSIGNED | NULL | 创建人 user_id（0=系统） |
| `update_by` | BIGINT UNSIGNED | NULL | 最后修改人 user_id |
| `created_at` | DATETIME | NOT NULL DEFAULT CURRENT_TIMESTAMP | 创建时间 |
| `updated_at` | DATETIME | NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP | 更新时间 |
| `deleted` | TINYINT(1) | NOT NULL DEFAULT 0 | 逻辑删除：0 正常，1 已删（MyBatis-Plus `@TableLogic`） |

标注「+ 乐观锁」的表再加：`version INT NOT NULL DEFAULT 0`（`@Version`，更新时 CAS）。

下文各表只列**业务字段**，末尾注明审计列形式：**A** = 公共审计列完整；**A+锁** = 公共审计列 + `version`；**仅时间** = 只建 `created_at`（流水表不可改）。

### 0.2 状态/枚举总表（与 03 文档状态机一致）

| 枚举 | 取值 |
|---|---|
| 周期状态 | `DRAFT` 草稿、`PUBLISHED` 已启动、`FINISHED` 已结束、`ARCHIVED` 已归档 |
| 方案状态 | `DRAFT`、`PUBLISHED` 已发布、`CLOSED` 已停用 |
| 目标状态 | `DRAFT` 待下达、`DISTRIBUTED` 已下达待确认、`CONFIRMED` 已确认、`DISPUTED` 员工提出异议 |
| 考评单主状态 | `DRAFT`、`SUBMITTED`、`DEPT_PASSED`、`HR_PASSED`、`FINAL_PASSED`、`CONFIRMED`、`RETURNED`、`APPEALING`、`IMPROVING`、`CLOSED`、`CANCELLED` |
| 评分阶段 | `SELF` 自评、`DEPT` 部门评、`HR` HR 复核、`FINAL` 终审 |
| 建议触发阶段 | `AFTER_SELF` 自评后、`AFTER_DEPT` 部门通过后、`MANUAL_RERUN` 人工重算 |
| 申诉状态 | `SUBMITTED` 已提交、`REVIEWING` 复核中、`SUSTAINED` 申诉成立、`REJECTED` 驳回、`WITHDRAWN` 撤回 |
| 改进计划状态 | `IN_PROGRESS` 执行中、`COMPLETED` 已完成、`CANCELLED` 已取消；任务态 `TODO/DONE/OVERDUE` |
| 审批节点/任务 | assignee：`ROLE/DEPT_LEADER/DESIGNATED_USER`；sign：`ANY` 单人/`ALL` 会签；任务态 `PENDING/APPROVED/RETURNED/REJECTED/SKIPPED` |
| 知识文档 | `UPLOADED/CHUNKED/EMBEDDING/READY/EMBED_PARTIAL/FAILED`；chunk 嵌入态 `PENDING/SUCCESS/FAILED/SKIPPED` |
| 检索模式 | `VECTOR` 向量余弦、`BM25` 关键词；`NONE` 未用检索 |
| 等级 | `S / A / B_PLUS / B / C / D`（展示层 B_PLUS 显示为 B+）；特殊值 `MANUAL_REQUIRED`（不给建议等级） |

> 等级编码统一用无特殊符号的 `B_PLUS`，前端字典翻译为 `B+`；后续字段中的"等级"均按此编码。

## 10. ER 关系说明（文本版，无物理外键）

### 10.1 组织与权限

- `sys_dept` 自关联树：一个父部门有 0..n 个子部门（`parent_id`），`ancestors` 冗余祖先链支撑"部门子树"数据范围查询。
- `sys_user` n:1 `sys_dept`（一个用户属于一个主部门；调岗只更新 dept_id，历史考评单的 dept_id 是快照不受影响）。
- `sys_user` n:n `sys_role` 通过 `sys_user_role`。角色固定 5 个，数据范围由 `sys_role.data_scope` 决定。
- `sys_message` n:1 `sys_user`（接收人）。

### 10.2 配置链：周期 → 方案 → 指标

- `perf_cycle` 1:n `perf_scheme`（一个周期可有多份按部门/岗位的方案；全员方案仅一份）。
- `perf_scheme` 1:n `perf_scheme_item` n:1 `perf_indicator`：指标库被多个方案复用；方案项是"指标在某方案中的权重/口径配置"。
- `perf_scheme` 1:n `perf_factor_config`（六因子权重）、1:n `perf_hard_constraint`（硬约束）、1:n `perf_grade_band`（六档）。三者与方案共版本号 `rule_version`。

### 10.3 目标链

- `perf_target` n:1 `perf_cycle` / `sys_user(employee)` / `perf_scheme`；唯一约束保证一员工一周期一份。
- `perf_target` 1:n `perf_target_item` n:1 `perf_scheme_item`（同时冗余 indicator/factor/weight 快照）。

### 10.4 考评执行链（主线）

- `perf_record` n:1 周期/员工/部门/方案/目标；`uk(cycle_id, employee_id)` 保证一员工一周期一张考评单。
- `perf_record` 1:n `perf_record_item`：明细项在考评单生成时从**目标明细 + 方案项**拷贝快照值（权重/目标值不可在考评阶段被方案侧改动影响）。
- `perf_record_item` 1:n `perf_material`（通过可空 `record_item_id`；另支持考评单级通用材料）；`perf_material` 1:n `perf_material_version`，材料每次更新追加版本，当前指针在 `current_version`。
- `perf_record` 1:n `perf_score_sheet` 1:n `perf_score_detail`；一张考评单每个阶段至少一张评分单；会签时同阶段多张，明细平均分回写 record_item 阶段分数列。
- 考评单状态与 `appr_task` 1:n：每次进入审批节点按 `appr_node_config` 解析生成一批 PENDING 任务（ANY 一个责任人即过；ALL 每人生成一行，全部 APPROVED 才过）。

### 10.5 建议与结论（核心留痕链）

- `perf_record` 1:n `perf_recommendation_snapshot`（只增；自评后、部门通过后各至少一版，人工重算追加）。
- `perf_manual_conclusion` 1:1 `perf_record`（当前生效），n:1 某一份 snapshot（终审依据）；结论每次修改 1:n `perf_conclusion_history`。
- 即：**引擎多版本快照 → 人工选一版（或据其调整）→ 结论留痕 + 变更历史**，任何修改在 `sys_operation_log` 还有动作级日志。

### 10.6 申诉与改进

- `perf_record` 1:n `perf_appeal`（业务上同时只允许一条未结案；历史申诉全部保留），申诉证据复用材料 id 列表。
- `perf_record` 1:n `perf_improvement_plan`（允许跨周期再建，但演示数据每单至多一条），计划 1:n 任务。
- 申诉本身可走 `appr_task`（biz_type=APPEAL，节点 APPEAL_REVIEW）。

### 10.7 智能域

- `ai_kb_document` 1:n `ai_kb_chunk`：文档重传→新版本→旧 chunk 逻辑删→重新切块；chunk 同时承载向量路（embedding）与 BM25 路（tags/keywords）。
- `sys_user` 1:n `ai_chat_session` 1:n `ai_chat_message`；消息中的引用反查 chunk/考评单（逻辑引用，不建物理外键）。
- `ai_chat_session` 1:n `agent_call_log`（从对话发起的调用）；独立页面发起的调用 `session_id` 为空，但日志必写。
- Agent 的 6 个只读/纯计算工具只读引用：指标库/历史方案（`perf_indicator/perf_scheme*`）、规则引擎 dry-run 结果（读 `perf_record*` 与 `perf_recommendation_snapshot`）、`ai_kb_chunk`、历史 `perf_record(status=CLOSED)`；Agent 不写任何业务表；`agent_call_log.adopted` 仅由人工确认接口在业务落库后回写。

## 12. 种子数据要求（db/seed.sql 必须覆盖）

1. 五个角色 + 1 个公司根部门 + 3 个二级部门（销售部/技术部/职能部）+ 每部门若干用户；五类角色各至少 1 个演示账号（文件头注释写明账号与统一初始密码，**不写任何真实密钥**）。

3. 一个 `2026-Q4` 周期（含四类截止时间）、≥ 8 个指标（定量/定性混合，覆盖 F1–F6）、1 套全员方案（默认权重/硬约束/分档直接按 04 文档 §4 落数）。
4. 全局审批节点配置：N1_DEPT（DEPT_LEADER，ANY）、N2_HR（ROLE=HR_SPECIALIST，ANY）、N3_FINAL（ROLE=EXECUTIVE，ANY）、APPEAL_REVIEW（HR 受理 + EXECUTIVE 裁定按两节点实现或单节点 ROLE=EXECUTIVE，默认后者）。
5. 四名"引擎验证员工" E1001–E1004 的目标、实际值、`aux_data`（出勤率/违纪等级与次数/培训学时/协作分/历史周期分，按 04 文档 §7 案例数值落）与各状态考评单，分别对应 04 文档 §7 的正常/临界/冲突/缺失四类案例。
6. 1 份虚构《绩效考核管理制度（演示样例）》文本及切块数据（embedding_status 先置 SKIPPED，配好 Key 后由管理按钮重建为 SUCCESS）。
